# Runbook

Operations that are deliberately not buttons in the product, and how to do them
safely. Everything here needs SSH to the server.

---

## Restoring the database from a backup

**This replaces every record in the hospital.** Read the whole section before
starting. There is no undo beyond the safety copy taken in step 3.

### Why this is not in the app

Restoring means executing a supplied SQL script against the live database. That
is the same shape as the Addons and System Update screens the parity plan
refuses (`docs/SETTINGS_PARITY_PLAN.md`, "Anti-parity"): content arriving over
HTTP that the system then runs. A single phished administrator session would be
enough to replace or destroy the entire record system, and a `.sql` file can do
considerably more than insert rows.

Taking backups, listing them and downloading them are all in the app —
Setup ▸ Settings ▸ Backup, Super Admin only. Only the execution step lives here.

### Before you start

- Know **why** you are restoring. A restore loses every change made since the
  backup was taken; if the problem is one bad record, fix the record.
- Tell whoever is using the system. Appointments booked during the restore are
  lost, and the app will error while the database is unavailable.
- Have the backup file on the server and know its size. A truncated download
  restores a truncated hospital.

### Steps

```bash
# 1. Get the backup onto the server (skip if it is already in /opt/smart-hospital/backups)
scp manual-20260810-221403.sql.gz ubuntu@SERVER:/tmp/

# 2. Stop the application so nothing writes mid-restore
sudo systemctl stop smart-hospital-api smart-hospital-web

# 3. Take a safety copy of the CURRENT database first.
#    If the restore is wrong, this is the only way back.
sudo -u postgres pg_dump smart_hospital | gzip | \
  sudo tee /opt/smart-hospital/backups/pre-restore-$(date +%Y%m%d-%H%M%S).sql.gz >/dev/null

# 4. Verify the file you are about to restore is intact and is what you think
gunzip -t /tmp/manual-20260810-221403.sql.gz && echo "archive OK"
gunzip -c /tmp/manual-20260810-221403.sql.gz | head -20   # header, PostgreSQL version
gunzip -c /tmp/manual-20260810-221403.sql.gz | grep -c 'CREATE TABLE'   # expect ~120

# 5. Recreate the database empty, then load the dump.
#    dropdb refuses while connections remain — that is the point of step 2.
sudo -u postgres dropdb smart_hospital
sudo -u postgres createdb -O smarthospital smart_hospital
gunzip -c /tmp/manual-20260810-221403.sql.gz | sudo -u postgres psql -v ON_ERROR_STOP=1 smart_hospital

# 6. Bring the schema up to the code's expectations. The backup may predate
#    migrations that this release needs.
cd /opt/smart-hospital/app/apps/api
sudo -u ubuntu env $(grep -h '^DATABASE_URL=' /opt/smart-hospital/app/.env) npx prisma migrate deploy

# 7. Start again and check
sudo systemctl start smart-hospital-api smart-hospital-web
curl -sf localhost:4000/api/v1/health && echo " api up"
sudo systemctl status smart-hospital-api --no-pager | head -5

# 8. Remove the copy from /tmp — it is a full patient database
shred -u /tmp/manual-20260810-221403.sql.gz
```

### If step 5 fails partway

The database is now half-loaded and unusable. Do not start the app. Repeat
step 5 using the **pre-restore** file from step 3 to get back to where you were,
then work out what was wrong with the backup before trying again.

## Backup files on the server

`/opt/smart-hospital/backups`, owned `root:hms`, mode 775.

| Prefix | Written by | Pruned |
| --- | --- | --- |
| `manual-*` | Setup ▸ Settings ▸ Backup | Yes — keeps the last N (default 10) |
| `pre-deploy-*` | `deploy/release.sh`, before every migration | Never automatically |
| `pre-restore-*` | Step 3 above, by hand | Never |

Pre-deploy files are the rollback point for a release, which is why nothing
removes them on your behalf. Clear them by hand when the disk needs it, keeping
at least the most recent one.

## Secrets in `.env.production`

`/opt/smart-hospital/shared/.env.production` is **regenerated by every deploy**.
`release.sh` reads back and preserves:

- `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` — rotating these signs everyone out.
- `SETTINGS_ENCRYPTION_KEY` — rotating this makes every stored SMS, WhatsApp,
  email and payment-gateway credential permanently undecryptable. It is
  generated on first deploy and preserved thereafter.

**Anything you add to that file by hand and is not in that list is lost on the
next deploy.** To add a new variable permanently, add it to the heredoc in
`deploy/release.sh` instead.
